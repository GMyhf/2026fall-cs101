# 课程大作业说明及评分标准

*Updated: 2026-10-18 (GMT+8)*

*Compiled by Hongfei Yan (2026 fall)*

## 一、作业目的

本大作业鼓励同学们从学习、生活或专业领域中的真实需求出发，将课堂所学的计算机基础、数据结构与算法知识应用于一个完整项目。项目可以规模不大，但应当目标明确、能够运行、结果可验证，并体现自己的思考。

通过项目实践，希望大家能够：

- **解决实际问题：** 识别使用者和使用场景，将需求转化为可实现、可检验的功能。
- **理解课程知识：** 说明算法与数据结构的选择，理解正确性、边界条件和时间、空间开销。
- **完成工程交付：** 经历需求分析、实现、测试、文档编写与版本管理的过程。
- **学会与 AI 协作：** 合理使用智能体（Agent），练习任务拆解、结果审查和独立验证，并对最终成果负责。
- **分享与表达：** 用清晰的代码、文档和演示，让他人理解、运行和使用项目。

## 二、选题与项目范围

### 1. 选题原则

优先选择自己确实遇到的问题。建议先完成一个最小可用版本，再根据时间增加功能。命令行工具、桌面程序、网页应用、算法实验或交互式学习材料均可，不要求都具备图形界面或公网部署。

项目应明确回答以下问题：

1. 为谁解决什么问题？现有方法有什么不足？
2. 本次计划完成哪些核心功能？怎样判断功能已经完成？
3. 使用了哪些课程知识？哪些部分体现了自己的设计、实现或验证？

### 2. 选题方向（建议但不限于）

| 方向 | 示例 | 可重点展示的课程知识与实践 |
| :--- | :--- | :--- |
| 游戏与搜索 | 五子棋、迷宫生成与求解、24 点求解器 | 状态表示、搜索、回溯、Minimax、Alpha-Beta 剪枝 |
| 算法可视化 | 排序过程、最短路径、树与图的遍历 | 算法实现、执行过程展示、复杂度比较 |
| 算法应用工具 | 素性检验、矩阵运算、文本匹配、压缩解压 | 数论、矩阵、KMP、Huffman 编码等 |
| 数据处理与分析 | 学习记录分析、关系网络分析、数据清洗工具 | 数据组织、查找与排序、图算法、结果验证 |
| 教学与学习工具 | 练习平台、错题管理、交互式讲义、Markdown 工具 | 数据建模、程序组织、自动化处理、测试 |
| AI 辅助应用 | 学习资料检索、答疑辅助、工作流程自动化 | 任务拆解、检索与数据处理、效果评估、失败案例分析 |

使用成熟库和框架是正常的工程实践。请说明它们承担的工作，并选择关键部分展示自己的理解；若项目主要调用外部服务，也应说明数据处理、系统设计与效果验证方面的具体工作。

仅整理课程笔记可以作为项目起点。若选择学习资料类项目，应进一步提供可运行的示例、自动化整理工具、检索功能或交互式演示，并验证其效果。

## 三、AI 与 Agent 的使用

### 1. 工具选择

为了便于学习和工作，不少同学已经自行开通了 Agent 订阅。此外，学校与阿里云公司协商并达成合作，为我校师生提供 **Qoder 智能体服务**，入口为：[https://aliyun.pku.edu.cn/](https://aliyun.pku.edu.cn/)。具体开通方式与使用规则以该入口说明为准。

大家可以根据已有条件选择工具，**不要求另行购买订阅，也不以使用某种工具或付费额度作为评分依据**。

### 2. 协作要求

鼓励使用 AI 辅助需求梳理、方案比较、代码编写、调试、测试和文档整理。AI 可以参与核心代码的生成；相应地，同学们需要能够解释其工作原理、检查关键逻辑，并用测试或实验验证结果。

建议采用以下流程：

1. **明确任务：** 写清目标、输入输出、约束和验收方式。
2. **分步实现：** 每次完成一个可检查的小功能，及时保存版本。
3. **审查与验证：** 阅读生成的代码，检查正常输入、边界输入和异常情况；对重要结论做独立验证。
4. **记录与反思：** 保留有代表性的协作记录，说明哪些建议被采纳、修改或否决，以及原因。

提交时，请在 README 中声明使用的 AI 工具、参与环节、本人承担的工作，以及验证方法。若未使用 AI，也请简要注明。无须提交全部聊天记录，可选取 1—3 个能体现判断与改进过程的例子，并删除其中的账号、密钥和个人信息。

### 3. 学术诚信与引用

允许参考开源项目、教程和 AI 生成内容，但必须清楚标注来源，说明复用范围及自己的修改，并遵守所用资源的许可要求。不得将他人成果直接作为自己的原创项目提交，也不得编造测试结果、运行截图或协作记录。

评价重点是你实际完成了什么、理解了什么，以及如何证明结果可靠。请确保能够说明项目架构、关键算法与实现、测试结果和已知局限。

## 四、技术与工程要求

- **编程语言：** 不限，可使用 C++、Python、Java、Rust、JavaScript 等。
- **核心功能：** 至少完成一个可以从输入到输出完整演示的主要流程，并明确其适用范围。
- **代码组织：** 按功能合理划分模块；涉及界面时，尽量将核心逻辑与界面分离。
- **运行环境：** 写明语言或运行时版本、依赖、安装步骤与启动命令；按需提供 `requirements.txt`、`package.json` 或 `Makefile` 等文件。
- **测试验证：** 覆盖主要功能，并包含适用的边界或异常情况。算法项目可与已知答案或简单实现对照；AI 应用应提供评估样例，说明成功与失败情况。
- **复现条件：** 提供示例输入、预期输出或演示步骤。依赖外部服务时，说明配置方法和限制；若评阅时无法访问该服务，应提供可检查的样例结果或演示材料。
- **数据与配置：** 说明数据来源，不将密码、API 密钥等提交至仓库。需要配置时，提供不含真实凭据的配置示例。

## 五、提交规范

### 1. Canvas 提交内容

请通过 Canvas 系统提交以下材料，截止时间以 Canvas 发布的通知为准。

1. **PDF 主文档：** 包含姓名、院系、项目名称、GitHub 仓库链接、项目核心截图，以及 README 的主要内容。若有在线演示，可一并提供链接；在线演示不能替代源代码与运行说明。
2. **原始文档附件：** 将 PDF 对应的 `.md`、`.doc` 或 `.docx` 文件上传，便于查阅。
3. **可评阅的项目版本：** 在 PDF 中注明最终提交对应的 Git commit 或版本标签，并确保评阅者能够访问仓库及所需材料。

### 2. GitHub 仓库命名与结构

仓库使用简明的项目英文名称，如 `SudokuSolver`、`GraphVisualizer`、`StudyTracker`。

以下结构供参考，可根据项目类型调整；`README.md` 必须提供，其余文件按实际需要组织。

```text
项目目录/
├── src/                 # 源代码
├── docs/                # 说明文档、截图与演示材料
├── tests/               # 测试用例或测试脚本
├── examples/            # 示例输入、输出或配置
├── README.md            # 项目主说明文档（必选）
├── LICENSE              # 按发布与复用需要选择合适的许可证
└── requirements.txt     # 依赖清单示例，按技术栈替换
```

### 3. README 内容清单

README 应让第一次接触项目的人能够理解并运行项目，至少包括：

- **项目背景与目标：** 面向谁，解决什么问题，已完成哪些功能。
- **课程知识与核心设计：** 使用的数据结构、算法及选择理由；适用时分析时间、空间复杂度或方案之间的取舍。
- **安装与运行：** 环境、依赖、配置、启动命令和最小使用示例。
- **功能展示：** 关键截图、示例输入输出或演示链接。
- **测试与结果：** 验证方式、代表性用例和实际结果，包含边界或失败情况。
- **局限与改进：** 已知问题、尚未完成的功能及后续计划。
- **来源与 AI 使用声明：** 引用资源、复用范围、AI 参与环节、本人工作与验证方法。

AI 使用声明可参考以下格式，并按实际情况填写：

```text
使用工具：……（未使用则注明“未使用 AI 工具”）
参与环节：……
本人完成的设计、修改与判断：……
验证方法及结果：……
代表性协作案例或记录位置（如有）：……
引用与复用的外部资源：……
```

## 六、评分标准（总分 100 分）

各维度分别评分后相加。以下描述用于说明评价依据，各项得分不预先限定在某个总评档次。

| 维度 | 分值 | 主要评价依据 |
| :--- | :---: | :--- |
| **核心功能与验证** | 30 | 目标明确，主要流程完整可运行；结果正确，有代表性的测试，能够处理或清楚说明边界与异常情况。 |
| **课程知识与理解** | 30 | 合理应用课程知识，能够解释关键数据结构、算法或系统设计；对选型、效率或效果有分析，并体现自己的判断。 |
| **代码质量** | 20 | 模块划分合理，命名清楚，代码可读；注释解释关键逻辑，避免明显重复及难以维护的实现。 |
| **文档与工程交付** | 10 | README 要素齐全，环境与运行步骤可复现，示例和截图有效；引用及 AI 使用声明清楚，提交材料完整。 |
| **创新与实用价值** | 10 | 对实际需求有观察，在功能、算法、交互或使用体验方面有自己的改进，并能用示例或反馈说明价值。 |

评分时将综合考虑以下表现：

- **优秀（90—100 分）：** 项目完成度高，验证充分，课程知识应用深入，能够清晰解释设计取舍与局限。
- **良好（75—89 分）：** 主要功能完整，课程知识应用正确，代码与文档清楚，存在少量不影响主要流程的问题。
- **及格（60—74 分）：** 达到基本目标，能够演示主要流程，但验证、分析、代码或文档仍有明显不足。
- **未达及格（低于 60 分）：** 主要流程无法完成，或提交材料不足以核验核心工作与课程知识应用。

项目规模、代码行数、界面华丽程度、工具价格及 AI 生成代码的比例均不直接决定分数。范围适当、实现扎实、理解清楚的项目同样可以获得高分。

## 七、建议的推进步骤与提交前检查

建议按“需求与验收标准 → 最小可用版本 → 测试与改进 → 文档与交付”的顺序推进，不必等全部功能完成后才开始写文档。

提交前请逐项确认：

- [ ] 主要流程可以完整演示，截图与最终提交版本一致。
- [ ] 按 README 在新的目录中安装和运行过，必要的依赖、示例和配置说明齐全。
- [ ] 已检查正常、边界或异常情况，并如实记录结果及已知问题。
- [ ] 能够解释关键代码、课程知识应用与自己的工作。
- [ ] 已标注外部资源来源和 AI 使用情况，仓库不含密钥等敏感信息。
- [ ] PDF、原始文档、仓库链接及提交版本信息齐全。
