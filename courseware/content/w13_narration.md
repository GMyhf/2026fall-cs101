## P6｜编译型 vs 解释型

两条路线。

编译型，比如 C 加加：源码经过编译器变成汇编，汇编器变成目标文件，链接器合成可执行文件，然后 CPU 直接执行机器码。

解释型，比如 Python：源码先被编译成字节码，然后由 Python 虚拟机逐条解释，每条字节码再去调用底层的 C 函数，最后才到 CPU。

下面的表做了对比。速度上，编译型直接跑机器码，解释型慢十到一百倍。跨平台上，编译型换平台要重新编译，解释型的字节码可移植。错误发现上，编译型在编译期就报，解释型要跑到那一行才报。对本课的影响：OJ 上 C 加加 的时限相对宽松，Python 常数大，要靠算法弥补。

这解释了一个常见困惑：同样是平方复杂度，C 加加 能过而 Python 超时。Python 的对策不是抠常数，而是换更优的算法。

## P7｜Python 的字节码

用 dis 模块可以直接看到字节码。

一个两行的加法函数，反汇编出来就是几条指令：载入 a、载入 b、做二元加法、返回。

每一条字节码，在解释器里都是一次循环迭代加一次函数分派。这就是 Python 慢的直接原因，也是「用 C 实现的内建函数替代 Python 循环」能提速的原因。

下面直接测：三百万次累加，纯 Python 循环大约零点一九秒，内建 sum 大约零点零四秒，相差五到十倍。因为 sum 的那三百万次循环发生在 C 里，没有字节码分派的开销。这正是第四周常数优化那一招的依据。

## P8｜CPython 的 GIL

全局解释器锁，简称 GIL：同一时刻只有一个线程能执行 Python 字节码。即使机器有十六个核，多线程也不能让纯计算并行加速。

所以，CPU 密集的任务，比如算数、循环，多线程没用，要用多进程 multiprocessing。而 I/O 密集的任务，比如读文件、网络，多线程有用，也可以用 asyncio，因为等待的时候会释放锁。

本课唯一用到线程的场景，是第八周讲的加大递归栈。那不是为了并行，而是为了绕开主线程固定的栈空间限制。

## P10｜进程与线程

四行对比。

地址空间：进程各自独立，线程共享同一个进程的地址空间。

创建代价：进程大，线程小。

通信：进程要走管道、共享内存或者 socket；线程直接读写共享变量。

崩溃影响：一个进程崩了只影响自己；一个线程崩了会拖垮整个进程。

一句话：进程是资源分配的单位，线程是调度执行的单位。本周只需要记住这张表，不要求你会写多进程、多线程代码。

## P12｜页表与 MMU：谁把「虚拟」翻译成「物理」

那虚拟地址怎么变成物理地址？

内存按四 KB 的页来管理。页表记录虚拟页到物理页的映射，由硬件里的内存管理单元，也就是 MMU，完成翻译。访问未映射的页，会触发缺页中断：操作系统要么去磁盘把页调进来，这是正常缺页；要么直接杀掉进程，这就是非法访问，也就是段错误。

对照第八周：递归太深、局部变量太多，栈这块区域被撑爆，触碰到未映射区，就是段错误或者递归错误。这就是「递归为什么会崩」的物理答案。

考场直觉：栈溢出和内存不够是两回事。前者是这一小块区域被撑爆，哪怕物理内存还很富余；后者是整个进程申请不到新页了。

## P13｜能申请 10¹⁸ 字节的内存吗

这一页用几个数字建立实感。

sys 点 maxsize 是二的六十三次方减一，说明这是个六十四位解释器。六十四位虚拟地址空间理论上约一点八乘十的十九次方字节，看起来够用；但实际的 CPU 只用四十八位虚拟地址，也就是二百五十六 TB。真正的上限是物理内存加交换空间。而且 Linux 允许超额提交：申请可能成功，真正写入时才内存耗尽。

## P16｜局部性原理

两种局部性。

时间局部性：刚访问过的数据，很可能马上再被访问，比如循环变量。

空间局部性：访问了某个地址，很可能马上访问它旁边的，比如数组遍历。

缓存就是靠这两条工作的。所以对缓存友好，就是顺序访问连续内存。这是第三周「存储层次」的直接推论：内存比缓存慢约一百倍，少一次内存访问就是省一大截时间。

---

## P17｜实测：按行遍历 vs 按列遍历

直接测一下。一千二百乘一千二百的二维列表，分别按行和按列求和。

按行遍历时，内层 j 变化，访问的是同一行里连续的元素，而且先把 a i 这一行取出来放在外面。按列遍历时，内层 i 变化，每次都要跳到另一行。

实测按行大约零点一二秒，按列大约零点一四秒，数值随机器波动，但方向一致：按行更快。

为什么 Python 里差距没有 C 那么夸张？因为 Python 的列表是指针数组，元素本身散落在堆上，缓存效应不如 C 明显。但「把 a i 提到内层循环外」同样有效，少一次索引就是少一条字节码。

## P20｜基本用法

先看文件读写的基本用法。

写文件，用 with 语句以写模式打开，指定 utf 八编码，用 write 写一行，用 writelines 写一批。读文件同样用 with 打开，最常见的是 for line in f 逐行读，每行去掉换行符再处理；也可以用 read 一次读完。最后用 os 点 remove 删掉临时文件。

with 语句保证文件一定会被关闭，即使中间抛了异常，比手写 open 再 close 更安全，本课统一用 with。

逐行读一次只在内存里放一行，大文件也安全；read 把整个文件读进内存，文件一大就危险。

## P21｜缓冲：为什么 print 很慢

为什么 print 很慢？因为每次 print 都可能触发一次系统调用。OJ 上输出上万行时，批量输出能快一个数量级。

代码里的做法是：把结果先攒进一个列表，最后用换行符 join 起来，一次 sys 点 stdout 点 write 写出去，只有一次系统调用。

输入同理：sys 点 stdin 点 read 再 split，一次读完全部，比多次 input 快得多。

考场速查两条：输出多行，先攒进列表最后一次写出；输入量大，一次读完再切分，别逐个 input。这就是第四周快速输入输出那一招，现在你知道它为什么有效了。

小结五条。

第一，编译与解释：解释了「同一算法 C 加加 过而 Python 超时」，Python 的对策是换算法，不是抠常数。

第四，局部性与内存：顺序访问连续内存更快；列表存一百万个整数约四十兆，bytearray 约一兆，OJ 限制常见六十四到二百五十六兆。
