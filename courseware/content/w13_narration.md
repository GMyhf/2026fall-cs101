## P3｜编译型与解释型

两条路线。

编译型，比如 C 加加：源码经过编译器变成汇编，汇编器变成目标文件，链接器合成可执行文件，然后 CPU **直接执行机器码**。

解释型，比如 Python：源码先被编译成字节码，然后由 Python 虚拟机**逐条解释**，每条字节码再去调用底层的 C 函数，最后才到 CPU。

关键差别在于中间多了一层：虚拟机逐条解释这一步，每一条都有开销。下一页看这个开销有多大。

---

## P4｜两者的差别与本课影响

五行对比。

代表语言：C 加加、Rust 是编译型；Python、JavaScript 是解释型。

速度：编译型直接跑机器码；解释型慢**十到一百倍**。

跨平台：编译型换平台要重新编译；解释型的字节码可移植。

错误发现：编译型在编译期就报；解释型要跑到那一行才报。

对本课的影响写在最后一行：OJ 上 C 加加 的时限相对更宽松；Python 常数大，要靠算法来弥补。

底下那句话解释了一个你多半遇到过的现象：**同样是平方复杂度，C 加加 能过而 Python 超时**。

## P5｜Python 的对策

那 Python 该怎么办？这一页给出对策：

**不是优化常数，而是换更优的算法。**

因为常数上你差着一到两个数量级，抠是抠不回来的；而换一个复杂度等级，能换回三个数量级。这和第四周那句「复杂度不对时不要优化常数」是同一件事，只是从另一个角度说了一遍。

## P6｜看看字节码

用 dis 模块可以直接看到字节码。

一个两行的加法函数，反汇编出来是五条指令：载入 a、载入 b、做二元运算、返回。

底下这句话说明了慢在哪：**每一条字节码在解释器里，都是一次循环迭代加一次函数分派**。而在 C 加加 里，同样的加法就是一条机器指令。

这就是那十到一百倍的直接来源。

## P7｜实测：Python 循环与内建函数

不用推理，直接测。

三百万次累加，纯 Python 循环大约零点一五秒；用内建的 sum 大约零点零三秒 —— **相差五倍**。

原因是 sum 是 C 实现的，那三百万次循环发生在 C 里，没有字节码分派的开销。

这正是第四周常数优化第三招的依据：**能用内建函数就用内建函数**。

## P8｜CPython 的 GIL

全局解释器锁，简称 GIL：同一时刻只有一个线程能执行 Python 字节码。

后果是：CPU 密集的任务，多线程**完全没用** —— 要用多进程。而 I/O 密集的任务，多线程有用，因为等待 I/O 的时候会释放锁。

对本课来说，用线程只有一个理由 —— 第八周提到过的，加大递归栈。而那一招在新版 Python 上对穿过 C 的递归也不管用。

## P10｜进程与线程

四行对比。

地址空间：进程各自独立，线程共享同一个进程的地址空间。

创建代价：进程大，线程小。

通信：进程要走管道、共享内存或者 socket；线程直接读写共享变量。

崩溃影响：一个进程崩了只影响自己；一个线程崩了会拖垮整个进程。

上一页说的 GIL，约束的是线程；所以 CPU 密集要用进程，代价是通信麻烦。

## P12｜「虚拟」的三个好处

为什么要多这一层翻译？三个好处。

**隔离**：进程 A 写坏自己的内存，碰不到进程 B。

**统一**：每个程序都以为自己从地址零开始，编译器不用关心它实际被装到哪里。

**超额分配**：虚拟空间可以大于物理内存，靠换页支撑 —— 这就是第二周那个交换分区。

最后一条是个实用的知识：Linux 允许**超额提交**，也就是申请内存时可能成功，**真正写入的时候才 OOM**。所以「申请成功」不等于「内存够用」。

## P13｜能申请 10 的 18 次方字节吗

这一页用几个数字建立实感。

sys.maxsize 是二的六十三次方减一，说明这是个六十四位解释器。

但一个整数对象本身就要二十八个字节，一个大整数三十六个字节；空列表五十六字节，一千个元素的列表八千多字节。

底下那句更要紧：**实际的 CPU 只用四十八位虚拟地址**，也就是二百五十六 TB；而真正的上限是物理内存加上交换空间。

所以「六十四位地址空间很大」和「你能用多少内存」是两件完全不同的事。

## P15｜Python 的内存管理

Python 用两套机制。

**引用计数**：每个对象记着有多少个名字指向它，减到零就立刻回收。这一页前半段用 getrefcount 演示了计数的变化。

但引用计数有个漏洞：**循环引用**。两个对象互相指着对方，计数永远不为零，谁也回收不了。

所以还有第二套 —— **分代垃圾回收**，专门处理这种不可达但计数不为零的对象。代码最后调用 gc.collect，确实回收到了东西。

这解释了一个现象：Python 里「删掉变量」不一定马上释放内存。

## P17｜局部性原理

两种局部性。

**时间局部性**：刚访问过的数据很可能马上再被访问 —— 比如循环变量。

**空间局部性**：访问了某个地址，很可能马上访问它旁边的 —— 比如数组遍历。

由此得到一条写代码的原则：**对缓存友好，就是顺序访问连续内存**。这正是第六周说「按行遍历比按列遍历快」的原因。

不过要说清楚一个前提：Python 的列表是**指针数组**，元素本身散落在堆上，所以缓存效应不如 C 明显。但「把频繁用的元素提到内层循环外」同样有效 —— 少一次索引就是少一条字节码。

L1 缓存一纳秒，相当于一秒。L2 缓存四秒。内存一点七分钟。固态硬盘随机读，一点二天。磁盘寻道，四个月。同城网络往返，十一天。

请盯着最后三行看一会儿。

底下那句是结论：**这张表解释了为什么「少读一次磁盘」比「少算一万次加法」更重要**。做算法优化时，先看有没有 I/O，再看计算。

## P19｜文件 I/O 与缓冲

具体到写法上。

读文件用 with 语句，它保证文件一定会被关闭，即使中间抛异常。逐行读对内存友好。

## P24｜一道综合例题的完整拆解

用一道题演示完整的思考流程。

题目：n 个任务，各有耗时和截止时间，任意顺序、不可中断，求最多能按时完成几个。n 是十万。

第一步，**看数据范围**：十万，只能线性对数，直接排除平方的动态规划。

第二步，**认题型**：「最多能选几个」，是贪心。

第三步，**想排序键**：按截止时间排序，先做快到期的。

第四步，**处理冲突**：一旦超时，就从已经选中的任务里丢掉**耗时最长的那个** —— 用一个大根堆维护。

第五步，**验证**：和暴力对拍。

请注意这五步的顺序：范围在最前，验证在最后，中间才是「想算法」。

## P25｜综合例题的实现与对拍

代码不到十行。

按截止时间排序，遍历：先把当前任务压进堆、累加总时长；如果超过了截止时间，就弹出堆顶 —— 也就是耗时最长的那个 —— 并从总时长里减掉。最后堆的大小就是答案。

为什么丢最长的是对的？底下那句给出了交换论证：丢掉耗时最长的任务，剩余总时长最小，对后面的任务最有利，而且任务数量正好减一，不吃亏。

这就是第六周那套论证方法的又一次应用。
